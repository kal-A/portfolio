# Informatica - Portfolio Implementation Instructions

## Positioning

Treat Informatica as an explanation-led Research, Product Strategy, and Project Planning experience page.

There are few or no direct public visual artifacts, so the page must earn credibility through clear explanation, reconstructed process visuals, and strong descriptions of the decisions Kamal supported.

Do not create fake product screenshots.

Narrative spine:

> Researching and organizing the work behind web applications and educational content, then turning it into clearer plans, workflows, and repeatable delivery.

## Core work to represent

Use the repository, resume, and prior confirmed notes to cover supported work across:

- UX research
- Product and project planning
- Organizing work for web applications
- Organizing educational web content
- No-code development
- Traditional web development
- Java-based frameworks where supported
- Classic frontend web development where supported
- Trello
- Microsoft Planner
- Microsoft Loop
- Research synthesis
- Requirements and task planning
- Content production workflows
- Blog-post automation using AI workflows
- PM support and coordination

Do not overstate engineering ownership. Be precise about whether Kamal planned, researched, prototyped, implemented, reviewed, or coordinated each piece.

## Suggested page structure

### Hero
Use a typographic and diagram-led hero rather than inventing a screenshot.

The hero should quickly communicate research, product planning, web-content delivery, workflow organization, and automation.

### 01. Turning scattered work into a plan
Explain the planning problem and how Kamal created structure around research questions, web app requirements, content work, owners, priorities, dependencies, and execution sequence.

Use a reconstructed planning map rather than a fake board screenshot.

### 02. Research that informed what to build
Show a research-to-decision flow:

`Question -> Research -> Synthesis -> Recommendation -> Requirement -> Plan`

Make the nodes interactive if consistent with the ForceN and Greenhouse diagram behaviour. Clicking a node should show a concise synopsis of what happened at that stage.

### 03. Choosing the right implementation path
Explain how work could involve no-code tools, Java frameworks, and classic web development.

The point is not to claim all three were always used together. Show that the implementation path depended on the content, complexity, maintainability, and delivery need.

A useful visual is a simple decision framework comparing speed, technical complexity, maintainability, flexibility, and handoff needs where accurate.

### 04. Organizing delivery
Explain the practical use of Trello, Microsoft Planner, and Microsoft Loop.

Show how they supported planning, task ownership, documentation, and continuity.

Avoid a logo wall. Each tool should have a reason for being there.

### 05. Automating content work
Explain the blog-posting AI workflow only as specifically as the evidence supports.

A useful reconstructed diagram:

`Content input -> AI-assisted draft or transformation -> Human review -> Formatting -> Publish or queue -> Verification`

Show Kamal's verification and judgment. Do not suggest autonomous publishing unless that actually happened.

### 06. Outcomes
Focus on the value of better structure and repeatability.

Potential categories, only when supported:
- less manual content-processing time
- faster movement from research to requirements
- clearer task ownership
- fewer handoff gaps
- more repeatable publishing or content workflows
- reduced rework
- faster delivery through choosing the appropriate implementation method

If a time-saved estimate can be derived from a documented manual baseline and automation frequency, calculate and label it transparently. Otherwise keep the outcome qualitative.

### 07. Reflection
Keep brief.

Strong themes:
- Research is useful when it narrows a decision.
- Planning tools matter when they clarify ownership and dependencies.
- Automation should remove repetitive work without removing human review.
- The simplest implementation path is often the right one when it still meets the product need.

## Visual direction

Use the existing Informatica colours first.

Reminder palette:
- light sky blue with a soft cauliflower-blue tone
- clean red accent
- warm off-white or near-white

Use subtle blue gradients, red for highlights or decision points, editorial diagrams, large typographic section headers, restrained cards, soft tinted panels, and dark borders with offset shadows consistent with the portfolio.

The page should feel intelligent and structured, not empty.

## Reconstruction rule

Every visual rebuilt after the fact must be clearly described as reconstructed.

Good reconstructed visuals:
- research synthesis flow
- planning framework
- implementation-choice matrix
- content automation workflow
- project coordination map

Do not create fake application screens, fake analytics dashboards, fake Trello or Planner screenshots, or fabricated user research artifacts.
